# Database access and transactions

## Reads and SQL

- Work backward from the API or job output to the SELECT list. Fetch columns needed for the result, assembly, cursor, and server-side decisions. Columns used only in WHERE, JOIN, or ORDER BY can stay in the database. Project list summaries in the query so the application never loads unused entities, large JSON fields, or blobs.
- Push filtering, aggregation, and pagination into the query where practical. For existence checks, use EXISTS or a one-row limit. Compute an exact count with the same predicates when the contract requires it. For continuation alone, follow the existing cursor contract.
- For several one-to-many relationships, page the parent rows first, deduplicate related keys, batch-fetch each relationship, and assemble in the original order. A simple relationship may take one join. Compare round trips, rows scanned, bytes transferred, and page correctness. Joining several child collections can multiply rows. Inspect executed SQL for lazy loads, queries triggered by serialization, and per-row implementations behind bulk method names.
- Bind parameters. An empty input must never cause a dynamic query to drop its WHERE clause. Preserve access rules and result ordering across batches. Size batches for parameter, payload, memory, and lock-duration limits. Query count should grow with relationship types and batch boundaries. Adding items within a batch should not add one round trip per item.
- Use a unique tie-breaker for ordering. For deep sequential paging, consider a composite cursor that matches the sort order. Preserve random page access, exact totals, or snapshot consistency when promised. One extra row can establish whether another page exists. Check ties, the final page, and concurrent changes against the contract.
- Check actual parameterized SQL, engine version, existing indexes, and representative data distributions. Design composite indexes around real predicates, joins, and ordering. Investigate implicit casts, functions on indexed columns, and large sorts or groups. Weigh read gains against storage, write amplification, and migration cost. A full scan, filesort, or long query alone does not establish a bottleneck.
- Start with an appropriate read-only execution plan, then verify counts and timing at the entry point. Distinguish estimates from measurements. Commands that execute the statement are subject to the project's data and environment restrictions. Prioritize frequent, costly operations while checking outliers that affect tail latency.

## Writes, locks, and recovery

- For a conditional update or delete, put resource identity, ownership, and required prior state in the statement. This avoids preliminary existence and ownership queries. Interpret row counts using the driver's semantics, including same-value writes. Query again only if the contract requires distinguishing outcomes the write result cannot identify.
- Establish whether a batch permits partial success or requires all-or-nothing execution. Preserve required auditing, triggers, references, accounting, and invalidation.
- Use a short transaction for writes that must commit together. Keep HTTP calls, object storage, model calls, encoding, and user waits outside the transaction where the contract allows. Connect cross-system stages using existing operation IDs, durable state, or receipts so interrupted work can resume at the right stage.
- Distinguish the database's own write locks from extra application-level exclusion. Avoid global locks, account-wide locks, preemptive locking reads, and nested locks without a demonstrated need. If cross-process exclusion is essential, reuse the project's supported mechanism. Where Redis is preferred, use a narrow key and account for expiry, release by the holder, and late writers. The authoritative store still enforces unique ledger entries, balances, and final commits.
- When changing a lock or batch write, exercise the actual competitors, such as two claims, duplicate callbacks, or an expired worker writing a late result. If a write's outcome is unknown, look up the original operation before retrying to avoid duplicate charges, generation, or submission.
